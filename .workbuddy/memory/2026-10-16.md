## 改写 deploy/ 下 FTP 上传/下载脚本（内网 OSS 传输）

**需求**：把本项目 `dist/img-sieve-linux-x86_64.tar.gz`（约 293MB）传到内网 OSS/FTP
服务器 `10.104.210.244:/project_amtp/dosp`，再在**内网服务器（python2）**上把它下载回来。
OSS 配置与远端目录保持不变。

**产出**：
- `deploy/ftp_upload.py` → Python 3（本机跑）
- `deploy/ftp_download.py` → Python 2 写法（内网服务器跑）

**关键决策与踩坑**：

1. **两个脚本语言版本不同**：上传本地跑用 py3；下载要在内网 py2 上跑，故用
   `print(...)` 单参数形式 + `float()` 显式整除 + `# -*- coding: utf-8 -*-`，
   控制台输出全 ASCII（避免 py2 unicode 写 stdout 报错）。

2. **REST 续传写法（重要，曾写错过）**：
   - 下载：`ftp.transfercmd("RETR file", rest=offset)` —— `rest=` 是关键字参数，
     ftplib 会**先单独发 `REST n` 再发 `RETR`**。
     ❌ 错误写法：`ftp.transfercmd("REST %d" % offset)` —— 把 REST 当传输命令发，
     服务端回 350 后连接空转，直接失败。
   - 上传：`ftp.storbinary("STOR file", fp, rest=offset)`。
   - ftplib 源码 `ntransfercmd` 对 REST 用 `sendcmd`（不校验返回码），故 350 合法。

3. **默认参数陷阱**：`def f(port=FTP_PORT)` 在**定义时**就绑定了值，
   运行时改 `FTP_PORT` 不生效（测试时被坑过一次）。改用 `port=None` + 函数内兜底。

4. **续传降级链**：上传按 `REST+STOR` → `APPE` → 全量 `STOR` 依次尝试，
   兼容不同 FTP 服务器对续传的支持差异。

5. 新增 `FTP_PORT = 21` 配置项（原脚本硬编码 21），便于测试与将来换端口。

**验证方式**（本机无 python2）：用纯标准库手写了个临时 FTP 服务器 + lib2to3
的 py2 grammar 校验，跑了 6 个用例全绿（上传 3 + 下载 3），含断点续传与 md5 校验。
测试产物已清理。

**遗留**：`deploy/downloadEsFile.py` 是早前 es_ivf_v2.tar 的脚本，与本次无关，未改动。

## 追加：给 ftp_upload.py 加 --force（17:41）

**用户遇到的问题**：远端提示"远端文件已完整存在，无需上传"，但服务器上的文件其实是坏的，
需要重新传。

**根因**：原来的"已完成"判定**只看文件大小**（`remote_size() == 本地大小`）。
大小校验只能挡住"没传完"，挡不住**内容损坏但长度恰好一致**的情况 ——
比如传输中被截断又补齐、磁盘静默损坏、内容被覆盖写入。

**解法**：新增 `--force/-f`
- 先 `DELE` 删除远端同名文件，再从 0 全量 `STOR`（不是用 REST 续传，
  否则会往坏内容后面追加，更糟）
- 删除失败不致命，会回退成覆盖上传
- 同时把 CLI 换成 argparse，`--help` 里能直接看到该用哪个参数

**同时改了提示语**：原来"远端文件已完整存在，无需上传"改为
"远端文件大小与本地一致，跳过上传" + 提示 `--force`。
措辞很重要 —— 原话会让人以为远端文件是好的，实际只校验了大小。

**验证**：构造了"远端大小与本地完全一致、但篡改 1 个字节"的文件，
复现用户的场景，3 个用例全过（默认模式跳过 / --force 修好 / 二次 force 幂等），md5 比对通过。

**教训**：任何"完整性校验"用大小都是不够的。要真正确认，只能比对
md5/sha（需服务器支持 XMD5/MLST 之类）或让对端自己校验。
